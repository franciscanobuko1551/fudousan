# Kokoro Navi AI 開発ルール

## プロジェクト名

Kokoro Navi AI

このリポジトリでは、ソースコードとREADMEに書かれている `Kokoro Navi AI` をプロジェクト名として扱う。作業フォルダ名や一時ブランチ名が別の語を含んでいても、プロダクトの方向性はソースコードとREADMEを正とする。

## 最終ゴールの仮説

Kokoro Navi AI は、人生相談、心のモヤモヤ、不安、人間関係、50代からの生き方、起業の悩み、自分らしい未来といったテーマについて、ユーザーが今の気持ちを言葉にし、安心して整理し、今日できる小さな一歩を持ち帰れるAI相談室を目指す。

最終的には、ユーザーが「否定されない」「急かされない」「気持ちが整理される」「次の一歩が見える」体験を安定して得られることをゴールにする。ただし、医療・法律・金融・緊急対応の代替にはせず、必要な場面では専門家や緊急窓口につなぐ。

## 現在のPhase

**Phase 0.5: AI相談体験プロトタイプ**

理由:

- 1画面の相談UIがある。
- OpenAI Responses API に接続できる。
- APIキーがない場合もフォールバック応答で体験確認できる。
- 相談ジャンル、深掘りボタン、回答コピー、新規相談、ブラウザ内履歴保存がある。
- 自傷・他害・虐待・DVなどの緊急性が疑われる言葉に対して、安全確保を優先する分岐がある。
- 一方で、ユーザー認証、サーバー側DB、正式な利用規約、プライバシーポリシー、体系的なテスト、回答品質評価、運用監視はまだない。

## 逆算したPhase計画

### Phase 0: コンセプト確認

目的: Kokoro Navi AI の人格、画面トーン、相談ジャンル、基本導線を確認する。

完了条件:

- プロジェクト名、README、基本UIがある。
- 相談を入力し、AIまたはフォールバックで回答が返る。
- 医療・法律・緊急対応の代わりではないことを画面で示している。

### Phase 0.5: AI相談体験プロトタイプ

目的: 相談体験として最低限の継続利用感を確認する。

完了条件:

- 深掘りボタンで回答の方向を変えられる。
- 相談履歴をブラウザ内に保存でき、保存しない選択もできる。
- 回答コピーと新規相談リセットができる。
- 緊急性が疑われる相談で安全確保を優先できる。
- `npm run check` が成功する。
- `npm run smoke` でトップページ、通常相談、緊急分岐、静的配信の基本安全性を確認できる。

### Phase 1: クローズドMVP

目的: 限られた利用者に試してもらい、価値と安全性を検証する。

完了条件:

- 利用規約、プライバシーポリシー、免責文言の下書きがある。
- 代表的な相談ケースのテストがある。
- 回答品質をレビューする観点がある。
- 相談履歴や個人情報をどう扱うかの方針が明文化されている。
- APIエラー、通信失敗、長文入力、履歴保存失敗の動作確認がある。

### Phase 2: 継続相談体験

目的: 単発相談から、安心して継続利用できる相談体験へ広げる。

完了条件:

- 相談テーマごとの質問テンプレートや整理フォーマットがある。
- 過去相談をもとに、ユーザーが自分の変化を振り返れる。
- 回答の安全性と品質を継続的に評価できる。
- 保存データの削除、エクスポート、同意管理の設計がある。

### Phase 3: 運用版

目的: 公開サービスとして安定運用できる状態にする。

完了条件:

- 本番デプロイ、監視、ログ、エラー通知がある。
- セキュリティレビューと安全性レビューを通している。
- 専門家・緊急窓口への案内を地域や状況に応じて改善できる。
- 回答品質を改善する運用フローがある。

## 開発ルール

- ソースコードとREADMEに書かれているプロダクト名と価値を正とする。
- AIは判断の代行ではなく、気持ちの受け止め、整理、小さな次の一歩の提案に徹する。
- 医療・法律・金融・緊急対応について断定しない。
- 自傷・他害・虐待・DVなど緊急性が疑われる内容は、安全確保と人間の支援につなぐ案内を優先する。
- ユーザーを依存させる表現や、専門家相談を遠ざける表現を避ける。
- 履歴保存はユーザーがオフにできる状態を維持する。
- サーバー側に相談内容を保存する機能を追加する場合は、事前に保存目的、保存期間、削除方法を文書化する。
- 画面文言、フォールバック応答、OpenAI用プロンプトの人格は揃える。
- Phaseが進むたびに、この文書の「現在のPhase」と完了条件を更新する。
- 変更後は最低限 `npm run check` を実行する。
- サーバー動作や配信範囲を変えた場合は `npm run smoke` も実行する。

## 安全ポリシーの補足

危機検知は、現時点では `server.mjs` のキーワード一致で行う。対象は、自傷、他害、虐待、DV、今すぐ逃げたいほどの危険など、AI相談だけで受け止めるべきではない内容とする。

危機検知に当たった場合の受け入れ条件:

- 共感よりも安全確保を優先する。
- 一人で抱え込まないことを伝える。
- 身近な人、地域の緊急窓口、医療機関、緊急通報への接続を促す。
- ユーザーの状況を断定しない。
- 「大丈夫」「必ず解決する」など根拠のない安心づけをしない。

通常相談の回答品質レビュー観点:

- 最初に相談してくれたことへの感謝がある。
- 感情を決めつけずに受け止めている。
- 状況整理が2〜3点程度に収まっている。
- 今日できる小さな一歩が具体的で、負担が大きすぎない。
- 医療・法律・金融などの専門判断を断定していない。
- 最後に希望が残るが、過度に楽観的ではない。

APIエラーや通信失敗時の受け入れ条件:

- エラーの詳細や内部情報を画面に出さない。
- ユーザーを責めない文言にする。
- 少し時間を置いて再送できることを伝える。
- 入力済みの相談文を不要に消さない。

localStorage利用時の注意:

- 相談履歴はこの端末のブラウザ内にだけ保存される。
- 共有端末では履歴削除を促す。
- 保存したくない相談のために、履歴保存オフの選択肢を維持する。
- Phase 1以降でサーバー保存を入れる場合は、同意、保存期間、削除方法を先に設計する。

## フォルダ構成の叩き台

### 現在の構成

Phase 0.5 では、ビルド工程なしで動かしやすい単純な構成を維持する。

```text
.
├── .gitignore
├── README.md
├── package.json
├── package-lock.json
├── index.html
├── styles.css
├── script.js
├── server.mjs
├── docs/
│   └── development-rules.md
├── scripts/
│   └── smoke-check.mjs
└── screenshots/
    └── .gitkeep
```

### Phase 1以降の候補

機能が増えてから、次のように分割する。

```text
.
├── docs/
│   ├── development-rules.md
│   ├── safety-policy.md
│   └── product-notes.md
├── src/
│   ├── public/
│   │   ├── index.html
│   │   ├── styles.css
│   │   └── script.js
│   ├── server/
│   │   ├── app.mjs
│   │   ├── openai-client.mjs
│   │   └── static-files.mjs
│   └── domain/
│       ├── consultation-policy.mjs
│       ├── crisis-detection.mjs
│       └── fallback-replies.mjs
├── tests/
│   ├── server.test.mjs
│   └── consultation-policy.test.mjs
├── screenshots/
└── package.json
```

今すぐ分割しない理由:

- 現在は小さなプロトタイプで、ファイル数も少ない。
- 先に分割すると、機能より構成の管理が重くなる。
- Phase 1でテスト、規約、保存設計が増えた段階で分割したほうが自然。

## 手動確認リスト

Phase 0.5では、リリース前や大きなUI変更時に次を確認する。

- 相談送信でフォールバック応答またはOpenAI応答が表示される。
- 「もっとやさしく」「具体的な一歩」「気持ちを整理」「未来への励まし」が押せる。
- 履歴保存をオフにした相談が履歴に残らない。
- 履歴削除でブラウザ内履歴が消える。
- 回答コピー後にボタン文言が戻る。
- 新しい相談で入力欄と回答欄が初期状態に戻る。
- 長文入力でやさしいエラーが表示される。
- 緊急性が疑われる入力で安全確保を優先した回答になる。
- `/server.mjs`、`/package.json`、`/.git/config` が配信されない。
- 不正なURLエンコードでサーバーが終了しない。
